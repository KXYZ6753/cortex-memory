## 1. Method

**GPU (unchanged from `i-energy.js`):**
- one window per question, [`at` − `wallMs`, `at`];
- `integrateBlocks` / `summariseEnergy` from `energy-integrate.js`;
- idle baseline from the `i-idle` windows: 6.61 W from 8 windows today, 8.18 W from 3 at night;
- design weighting 0.068 × miss + 0.932 × hit.

The GPU columns reproduce v5-final's Table 3 and the journal exactly. For example, FULL-3 GPU J per correct answer: gates 99, lite 175, x1 205, q1 237.

**CPU sampler** (`i-cpusampler.js`): about once per second it logs the machine's busy % and the cumulative CPU seconds of every node / llama-server / ollama process.
- Span: Wed 10:54:50 ET to the end, so the FULL-2 arms other than lite (09:36–10:52 ET) predate it.
- Each pid's samples are split into segments at gaps over 5 s or where the cumulative value drops, because Windows reuses pids. At night, 5 llama-server pids were reused.
- A process's CPU seconds in a window are interpolated linearly from its cumulative samples.

**Runner detection:**
- Candidates are node segments alive over the whole run. Excluded: the energy logger (2016), the sampler (15192), and any segment alive for the sampler's whole span.
- The runner is the candidate with the most CPU seconds inside the run's question windows.
- `--pid set:variant=pid` overrides the choice; it was not needed.
- Reported with the runner-up, its birth and exit relative to the run, and two checks:
  1. the correlation of per-question runner CPU with the question's non-generation time (`wallMs − genMs`);
  2. its CPU per path, deconvolved from the 1 Hz samples. Each sampler interval's runner CPU is regressed on the seconds of each path's windows (and of gaps) inside the interval, with OLS and no intercept.

**CPU energy.** A run's own processes are the runner, every llama-server and ollama. During a run the GPU lock means the only llama-server doing work is the run's: each variant gets a fresh one, born 1–3 s before its first window.

- **Package power model.** Package W = a + b × busy %, fitted on 10 s block means. J per CPU-second = b × 100 / 16 logical CPUs.
  - Today: a = 41.5 W, b = 1.339, R² 0.90 over 1,497 blocks, giving **8.37 J per CPU-second**.
  - Night: a = 43.0, b = 1.391, R² 0.91, giving 8.69.
- **Why 10 s blocks and not i's 1 s pairs.**
  - LibreHardwareMonitor's 1 Hz package reading and Get-Counter's 1 s busy % are not aligned. The misalignment is noise in the regressor, so it pulls the slope towards zero.
  - Today's 1 s fit gives b = 0.78 (R² 0.38) at lag 0. With the CPU sample shifted −0.5 s it gives b = 0.96 (R² 0.56). Over 5/10/30/60 s blocks the slope is 1.28/1.34/1.37/1.37, with R² 0.86–0.93.
  - At night (less background load) the 1 s fit was less attenuated: 1.25, R² 0.81; on 10 s blocks, 1.39.
  - So the 1 s slope used for v5's q1 figure (0.81 W per %, 5.0 J per CPU-second) understated CPU energy by about 40%. The 10 s slopes agree between day and night (8.4 vs 8.7 J per CPU-second).
- **A (primary): slope × own CPU-seconds.** This is i's method with the fixed fit and the runner included.
- **B (check): direct share.** In each 10 s block, package power above the floor a is shared out by CPU seconds: own ÷ max(machine busy, own). B equals A within 1 J/q on every run, as it should when the linear model fits.
- **C (sensitivity): a slope per process group.** Block-mean package W is regressed on the CPU rates of the runners, llama-server, ollama and the rest of the machine.
  - Today: runner 9.0, llama-server 17.6, ollama 14.6, rest 7.5 J per CPU-second (R² 0.94).
  - Night: runner 6.1, llama-server 9.0, ollama −28 (ollama is almost idle at night), rest 8.9.
  - The extra cost of a llama-server CPU-second does not replicate between the two logs. It probably picks up uncore and IO-die power while the GPU generates. C is therefore shown only as a sensitivity. It adds 5–16 J/q and leaves every ordering unchanged.

**Totals:**
- **total (gross) = GPU gross + CPU A.** This is the basis of the round-5 tables, which quote GPU gross.
- **total (marginal) = GPU marginal + CPU A.** This is `i-energy.js`'s "total".
- **Not counted:** the CPU package's static floor (≈ 41.5 W, about 32 J/q for gates and 96 J/q for q1), DRAM, disk and PSU losses. The "box-level" column in `e2-energy-r5.md` (GPU gross + floor × wall + CPU A) shows that counting the floor widens the ratios further (q1/gates 2.74× on FULL-3).
- **Upper bound for runs without the sampler:** all package power above the floor inside the windows. It includes other workers' CPU jobs.

Why these are the runners:
- **Birth times match the launches.** Every pid is born within 1 s of its command's start in `lite-chain.log` (11:42:10, 12:38:19, 12:57:17, 13:12:04, 13:24:37, 13:42:40, 13:56:56). The lead's single-command runs are born 3–5 s before their first window: process start, pool load, model load and the two warm-up calls.
- **Exit times match too.** Each process exits within 1 s of its last window. A chained lead command starts a new process for each `cli2 run` (6860 follows 10092; 17224 follows 20652), and a multi-variant command keeps one process (23392 for FULL-3's three arms).
- **Queued processes are idle.** A process queued on the GPU lock uses about 1 CPU-second over 13–40 min, so it never competes. This is the source of every runner-up at 0.000–0.001 s/q.
- **The CPU follows the cross-encoder.** The runner's CPU correlates with non-generation time at r = 0.90–0.99 (0.58 for gates, which uses almost no runner CPU); the runner-up's is ≤ 0.2. By path, the runner's CPU is about 0 on plain commits and g5 handovers (deconvolved −0.2 to 0.2 CPU-s/q). It is 4.7–5.1 on the explore path (x1's cross-encoder explore list) and 8.0–9.8 where m2 fires (the recovery list over the mailbox's BM25 top 50) (§7).
- **Other workers' node processes** (analysis scripts) run beside the runs. One used 1,044 CPU-seconds in 3 minutes during FULL-3's x1 run. None of them is alive across a whole run with comparable CPU, so none is a candidate.
- **The night runs** (worker i's logs) give the same picture: runner pids 22776 (det x1), 28396 (det gates), 30196 (det t-lk), 28876 (pb, x1) and 24012 (gates, t-lk). These are the pids in `i-pids.txt`. r = 0.91–0.98 (0.45–0.63 for pb and gates).

- **An m2 firing costs about 9 CPU-seconds**, not 1.1–1.4 s. Its non-generation time is about 1.3 s longer than a commit's, and during that time the runner keeps about 7 cores busy.

## 8. Does the frontier change?

**The order does not change.** In J per correct answer it stays gates < lite-det-ub < det x1 < q1:
- under GPU only, GPU gross + CPU, GPU marginal + CPU, the by-group slopes (C) and the package upper bound;
- on FULL-3 (all measured), FULL-2 (lite measured; others imputed or bounded), S300-1 and S300-2/3.

## 10. Caveats

- **Attribution is approximate.**
  - The 10 s fit explains 90% of the variance in package power.
  - A CPU-second is priced the same whatever the process (A). The by-group fit (C) suggests llama-server's CPU-seconds coincide with dearer package power on today's log but not at night. Under C the CPU numbers rise by 5–16 J/q, and the ratios move by at most 0.03.
- **1 Hz sampling.**
  - Per-question CPU is smeared over about ±1 s, so path figures use the deconvolution.
  - Run totals are exact to within the 1 s at each end.
  - Interpolated and deconvolved runner CPU agree within 0.2–0.7 CPU-s/q on every CPU-heavy path.
- **Excluded:** the package floor (about 41.5 W while anything runs), DRAM, disk, the motherboard and PSU losses.
  - **Box level.** Adding the floor × wall time (GPU gross + floor + CPU A, in `e2-energy-r5.md`) penalises slow systems further: FULL-3 gates 145, lite 286, x1 318, q1 397 J per correct answer.
- **The FULL-2 CPU rows for gates, x1 and q1 are imputed** from FULL-3's rates (§4). Only lite-det-ub is measured on FULL-2.
- **Other workers' load.** The CPU sampler cannot see other workers' work inside ollama (for example, CPU embedding calls). ollama's CPU during runs is 0.02–0.12 s/q, so the effect is small either way.
- **Det arms vs unwrapped runs.** All fresh-set arms are det arms. det's resets are GPU calls, so they show up in llama-server CPU (1.0–1.6 s/q), not in runner CPU.
