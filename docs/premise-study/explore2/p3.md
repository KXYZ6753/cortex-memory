## 2. confirm2.js for several arms

**The addendum's machine-readable lines** (`parsePrereg`, each on its own line):

```
Arms: q-det-q1, lite-det-ub, i-det-x1
Verdict key prefix (q-det-q1): `X-explore2-q1|small|<questionKey>`
Verdict key prefix (lite-det-ub): `X-explore2-lite|small|<questionKey>`
Verdict key prefix (i-det-x1): `X-explore2-x1|small|<questionKey>`
Code hash: `<64 hex>`
```

**What parsePrereg checks:**
- The first arm listed is the confirmatory one, and TEST runs take the arms in the listed order.
- Required: exactly one `Arms:` line; exactly one prefix line per listed arm, of the form `X-explore2-<short>|small|<questionKey>`; distinct prefixes; no prefix line for an unlisted arm; exactly one filled `Code hash:`.
- p2's single-arm lines (`Arm:` and `Verdict key prefix:` without an arm) are refused, so a stale draft cannot pass.

**Guard order on `run <arm> [n]`** (p2's order, unchanged; nothing from TEST is read before steps 1–2 pass):
1. **Pre-registration.**
   - The addendum is committed and clean, and lists the arm with its prefix.
   - Its code hash equals `codeHash2()`.
   - explore2/ and the import closure (now 88 files) are tracked and clean.
   - explore/ still has `9801148b…`.
2. **Environment:** a registry arm; the Ollama build and e2b digest are the main run's; the generation options equal `run-state.json`'s (num_predict 160).
3. **Items and order.** The TEST item list is read (`confirmRecords`).
   - **New:** every arm listed before the requested one must have all n questions done in its own store (`ExploreStore.done`: a final answer, or 3 failed attempts). Otherwise the run refuses before any GPU or energy work.
4. **Under the explore2 GPU lock** (as p2):
   - the logger and sampler are started and verified, and the runner pid is checked in the sampler;
   - fresh model load, two warm-ups, a 30 s idle baseline, blocks of 50;
   - logger and sampler are stopped as a process tree;
   - pids go in `manifest.jsonl`.

**Store dirs:** one per arm. TEST: `.data/premise2/explore/confirm2/<arm>/`; dry-run: `.data/premise2/explore/confirm2-dryrun/<arm>/`. Each holds answers, markers, energy, cpu, manifest and verdicts. `armDirOf` refuses arm ids that are not `[A-Za-z0-9_-]+`.

**`grade <arm> [--plan]`**
- tier-a.js on the arm's latest final answers (confirmUnits' rule), with cell id = the arm's prefix from the committed addendum.
- Verdicts go to `<arm dir>/verdicts.jsonl`; spend phase `confirm2`.
- **Adjudicator evidence = `readPaths`, else `contextPaths`** (as confirmUnits). I checked what the arms store:
  - every explore2 arm sets `readPaths` (explore/variants.js documents it as "emails the final answer call saw"), so `contextPaths` is never needed;
  - one-shot / commit / recover paths store the final context, plus W1 when the abstention retry ran;
  - a g5 handover stores g5's final read set (`readSet`);
  - `finalPaths` does not exist in these arms.
- **Reuse:** verdicts already present under the same key (main study, `confirm/verdicts.jsonl`, the other arms' files) are reused, as verdict keys are the main study's. `--plan` prints counts only.
- **Guards:** grade and analyze need the committed addendum (arm list and prefixes). Other guard problems are logged and written to the output, not fatal, because the answers already exist.

**`analyze`** writes `benchmarks/results/premise2/explore2/confirm2.{json,md}`.
- **Primary family** (Holm over three; scoring by confirm.js `scoreWith`; estimator as analyzeConfirm):
  - Z1: q1 − e2b P-B, superiority;
  - Z2-NI: q1 − 31b P-B, non-inferiority at 5 points;
  - Z3: q1 − gates, superiority. gates = confirmUnits from addendum 3's store with `overflowIsWrong`.
- **Secondary:**
  - for q1: excluded-failures sensitivity, J1-only, and 31b superiority;
  - for lite and x1: Z1/Z2-NI/Z3, each also excluded and J1-only;
  - each arm − q1, plus J1-only; lite − x1;
  - Z1 on all questions run, if an arm has more than 600.
- **Per arm** (and gates):
  - tier-A accuracy on the 600; unresolved, overflow and technical counts;
  - latency mean/p50/p95/max; calls, real and including resets;
  - path mix (e2-energy's `pathOf`); det resume points (1–99 counted);
  - energy on both bases.
- **Sensitivity rule:** "excluded" removes the arm's context overflows **and** technical failures after 3 attempts (statuses outside FINAL_STATUSES), following addendum 3 §6's text. analyzeConfirm removes only overflows, which makes no difference for gates (600/600 ok).
- **Energy, per answer and per correct answer:**
  - **Block basis:** addendum 3's.
  - **Attribution:** e2.md's method A, with B as a check.
    - The J per CPU-second comes from the run's own 10 s-block fit, falling back to the round-5 8.37 if there are fewer than 30 blocks; the source is stated in the JSON.
    - **Runner pid:** taken from each session's manifest. gates has no manifest, so its runner is detected as e2.md does: the node segment alive over the whole run with the most in-window CPU. The loggers' pids from `confirm-run.log` are excluded, and the runner-up and r are reported. `CONFIRM2_GATES_RUNNER_PID` pins it.
    - gates' sampler log is `confirm/cpu.jsonl`. The 355-question run's separate `cpu-355.jsonl` is not used, because only the 600 are analysed.
- **Comparators' energy:** the main study's report figures, as analyzeConfirm.
